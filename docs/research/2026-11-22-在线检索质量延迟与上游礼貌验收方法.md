# 评价依据研究：在线检索质量、延迟与上游礼貌的验收方法

日期：2026-11-22（Asia/Shanghai）
关联：Wayfinder 地图 [#31](https://github.com/Drivpe/kingdee-knowledge-core/issues/31)，研究票 [#35](https://github.com/Drivpe/kingdee-knowledge-core/issues/35)
代码基线：`9d636962e3cf96c848973b0c8911cffa74e6c829`（`research/quality-evaluation-35` 的起点）
范围：匿名、个人低并发、三端复用的金蝶社区检索与证据；不评价答案生成、语言选择或 UI；不修改内核源码。

> **结论先行：在线自动采样目前不能直接启动。** 本轮仅对上游做了一次 robots 规则核实（以及公开首页/协议页的有限查看），没有调用搜索、详情或回答 API，没有做延迟测量、并发试验或压力测试。
> 2026-11-22 取得的 [`vip.kingdee.com/robots.txt`](https://vip.kingdee.com/robots.txt) 明确含 `User-agent: *` 与 `Disallow: /`，仅另列 Googlebot 等特定爬虫的允许规则。RFC 9309 §2.2.1、§2.2.2、§2.3.1 要求 crawler 使用匹配组并遵守可解析规则；robots 规则是访问偏好，不是授权，404/4xx 与 5xx/网络不可达的处理也不同 [S1]。当前内核的浏览器形 UA 并不构成上述具名例外，也没有理由把“匿名、GET、低频、个人”当成例外。
>
> 因而下文在线部分是**取得上游许可/规则适用解释后的候选协议**，不是本轮已执行的验收。不能把 robots 的 crawler 语义偷换成“所有 API 调用法律上必然禁止”，也不能把它反过来说成 API 已获授权；需维护者与上游明确本项目程序化调用方式。找到/未找到 SLA 同样不改变这一前置条件。

## 1. 可交付结论与边界

### 1.1 建议采用四层、可分别归因的验收

1. **人工金标与快照**：保留原始问题、信息需求、版本/产品范围、文档及证据段落的人工判断；保存经许可取得的不可变响应，而不是把一次在线输出当“永久真值”。
2. **固定查询计划下的内核 search**：在完全相同关键词、产品过滤与冻结上游响应上，测量已知相关帖的 `Hit/Recall@10`、首个相关帖的 reciprocal rank，必要时报告分级 `nDCG@10`。它回答“给定这些词，内核有没有把已知好材料带回来、排在何处”。
3. **宿主自动选词、候选选择**：不预先给宿主参考答案，在留出原始问题上自动选词；与固定计划比较，差异归因于宿主选词。对相同候选清单测 `selection@K`（选到好帖且没有以无关帖挤掉名额），选择消耗单独记账。
4. **read 全文与证据充分性**：对固定文档标识评价是否完整取得所需原文/回答、证据片段是否可追溯，产品范围与截断是否可见。另行测自动选文后的任务成功率；**召回高分不等于证据可用，采纳/点赞/标题相似不等于回答正确。**

在线延迟、请求、字节、token、缓存命中、失败和截断是**独立的运行预算与新鲜度维度**，不得揉进一个检索总分。可用少量定义良好的指标，不做大规模 SRE 监控平台、向量索引或 LLM-as-a-judge 先行方案。

### 1.2 本仓已有与没有证明的东西

- [`tests/baseline/public-behavior-baseline.json`](../../tests/baseline/public-behavior-baseline.json) 的 `scenarioCount: 41` 是固定 fake 上游的公开行为录制，`elapsedMs` 被归一化，限速不参与基线，保留的是请求参数、次数和结果键序 [L1]。`tests/kd_regression.py` 与 baseline 重放只证明在**已选 fake 输入**上的行为是否保持，不能证明在线上游整体相关文档的召回、真实延迟、可靠性和证据充分性。
- 每词一路、每路首页 10 条、按首次路序和该路内上游名次去重归并，见 [`_manifest.py`](../../src/kd/_impl/_manifest.py#L80-L114)、[L224-L259](../../src/kd/_impl/_manifest.py#L224-L259)。所谓“零算法排序”不是无排序：调用方路序仍是第一排序键；应测它与宿主选词的交互，而不是先断言它优于其他融合。
- question read 的问题详情 1 次、回答首页 1 次、余下 `P-1` 页，再对前最多 `maxDetail=5` 条回答发详情请求，见 [`_detail.py`](../../src/kd/_impl/_detail.py#L93-L193)。在失败、重试、重定向不计入时，其当前**尝试数**是：

  ```text
  search:   D = 去重并截断后的关键词路数，D <= 7
  question: N = 1 + P + min(A, 5)
            P = totalPages（首页响应给出，不预设上限）
            A = 已取得的回答列表条目数
  ```

  因而 `N` 并非恒为 `1 + P + 5`；0–5 条回答时不发 5 次详情。不能给当前 read 承诺固定请求上限，更不能把分页“并发度有界”写成“总请求数有界”。
- `_get_json` 固定 20 秒 socket 阻塞操作超时，没有应用重试/退避/总 deadline；速率限制与 `upstreamCalls` 是进程内状态 [`_net.py`](../../src/kd/_impl/_net.py#L95-L111)、[`_config.py`](../../src/kd/_impl/_config.py#L475-L561)。`stats.elapsedMs` 用 wall-clock `time.time`，见 [`_public.py`](../../src/kd/_impl/_public.py#L154-L160)，而限速等待另用 monotonic clock。三端并发不能用这个计数器证明每个调用者的独立预算。
- 现有 ADR 曾记录 23 例/12 例历史评测及旧缓存负收益/收益，但原始评测资产已迁出，且对象、内核和前提不同 [`ADR-0003`](../adr/0003-cache-opt-in-and-retrieval-verdicts.md)。它可以提示指标与风险，不能替代本轮冻结金标和在线基线。旧 ADR 的“无 429/限流头”也不能证明无长窗口限速或 SLA。

## 2. 小型领域金标：怎么建，怎么不自我证明

### 2.1 以“信息需求”而不是以查询字符串为单位

NIST 对 test collection 的定义是文档集合、topics（信息需求）和 qrels（相关性判断）；topic 是意图，query 是用户实际输入，run 是系统输出，pooling 常取各 run 的 top n 文档供评估 [S2]。本仓应把这些拆成：

| 字段 | 必须保存的内容 | 防什么偏差 |
|---|---|---|
| `topic` | 原始用户问题、意图、期望证据类型、产品线/版本、时间 | 让金标只适配某个检索词 |
| `queryPlan` | 人工固定 `keywords[]` 及其顺序、过滤条件、形成者与日期 | 固定输入下重放与比较内核 |
| `qrels` | 每个候选帖 `relevant/partial/irrelevant/unjudged`，判断理由与范围 | 不把“未标”静默当成“无关” |
| `evidence` | 回答/正文段落定位、支持的要点、快照与原文 URL | 区分“主题相关”与“证据确实够用” |
| `run` | 系统/内核/宿主版本、输入、请求 URL、响应哈希、时间 | 能解释每次分差来自哪一层 |

查询集以真实或刻意采集的代表性任务为来源，先划定产品、任务类型（机制/报错/配置步骤/概念）、语言形态、常见/困难问题和明确无答案/不应给答案任务，再分层保留一小批，而非只选“知道能搜到”的问题。初始可用 30–50 个 topic 做建集与试标，**这只是起步工作量，不是证明统计充分的数字**；留出开发/调参集与最终未碰过的测试集。新增、修改金标要有版本、日期和理由，不得看到新系统输出后悄悄改判去迎合它。

### 2.2 候选池与人工标注

- **先定规则和大部分金标，再跑被比较的系统**。可用手工已知资料、历史合法产物、不同检索策略的候选做初始池；任何新的自动候选收集均受第 8 节的上游规则前置条件约束。
- TREC pooling 支持把不同 run 的前部候选汇总给 assessor [S2]。本仓小集可把**所有待比较变体**的不同 top-k 候选合并、去重，再让标注者盲评。否则只从现任系统取候选会系统性偏袒它。
- 标注者看原始 topic、预期产品/版本与候选正文；不要显示系统名、原始名次、点击数或推荐分，避免位置与实现暗示。随机候选展示顺序，并保存原路序供事后分析。
- 使用清楚的三档或四档操作性判据，例如：`2 = 直接支持所需结论/步骤`；`1 = 只覆盖部分必要条件`；`0 = 不满足此 topic 的证据需要`；`U = 未判断`。这里“分级”对应证据用途，不是社区采纳/点赞的另一写法。
- 至少对一批覆盖各类型的 topic 做**双标 + 分歧裁决**，保存原始两人判断和裁决理由；有领域歧义时先改指南，而不是平均成小数。NIST 的研究说明不同 assessor 的判断集合可以变化，而足够大的 TREC 集仍能稳定给出系统相对排序 [S3]；这不免除本仓小集的双标抽查，也不能保证单条判断“绝对正确”。
- 可把排序比较难解的少量文档做 A/B 偏好判断。原研究在六名 assessor、51 个真实查询上发现偏好判断比五级绝对判断更快，并提高了真实偏好相对于由绝对判断推导偏好的一致性 [S4]；但**缺失偏好的鲁棒性仍是其明确开放问题**，所以本仓只将其用于疑难对照，不取代所有 qrels。
- 文档内容可能更新或删除。`topic_id + doc_id + snapshot_hash` 才是离线证据的准确身份；只按 URL 会把后来改过的正文误当原文。动态集合的不完整和 imperfect judgments 都是已知问题 [S5]。

### 2.3 “已标金标召回”与“全集召回”不是一回事

对本仓可合理构造的小型金标，可计算 `knownGoldRecall@k = |G ∩ R_k| / |G|`，其中 `G` 是该 topic 已确认的相关帖集合。它是“已知金标被找回的比例”，**不是匿名社区全集的真实召回**。没扫过全库、也没完整独立 gold 时，分母不是全库相关文档数。

Buckley 与 Voorhees 证明，普通指标在判断严重不完整时不稳健；bpref 仅使用已判断的相关/不相关文档，对不完整判断更稳健，但对“某个位次进入标注池是否与相关性独立”及新系统候选仍有前提和开放问题 [S5]。因此首选仍是补足本仓小集的多来源人工标注并报告 `U`，不是用 bpref 或 `trec_eval` 消除未标注偏差；`trec_eval` 只负责算分，不证明金标代表在线社区。

## 3. 召回与排序：小指标组合及其局限

以下都在**冻结同一 run/qrels**上计算，按 topic 宏平均；同时附每 topic 明细，不只报均值。

| 指标 | 本仓定义/用途 | 局限与误读防护 |
|---|---|---|
| `Hit@k / Success@k` | 前 k 至少有一个 `rel >= 1` 的 topic 比例 | 一个相关命中即饱和，掩盖其余证据漏召；困难/无答案集必须单列 |
| `knownGoldRecall@k` | 前 k 找到的已标相关帖 / 该 topic 已标相关帖数 | 依赖 gold 完整度；首页截断造成的已知漏召可见，不代表全集召回 |
| `P@k` | 前 k 中已标 `rel >= 1` 的帖子数 / k | 候选不足 k、U 的处置必须固定；衡量清单噪声，不衡量“是否读对全文” |
| `RR` / `MRR` | 每 topic 首个相关帖名次倒数 `1/rank`，未命中记 0，跨 topic 求均值；NIST 文献中的定义同此 [S6] | 只关心第一个相关，不关心其余相关；无答案与无命中均 0，须分别列计数 |
| `nDCG@k` | 用分级 gain，并除以已知金标构造的理想前 k 排序 | gain、折扣和理想排序是评价模型，不是天然真值；U 的处理和变体须固定 |

`nDCG` 的原始动机是把“高度相关比边缘相关更有价值”和“越靠后用户收益越小”同时纳入评价，并以已知相关集合构造 ideal，而不是假设所有位置都是最高相关 [S7]。本仓若采用常见变体，应明确写出并版本化，例如：

```text
DCG@k = sum(i=1..k, gain(rel_i) / log2(i + 1))
nDCG@k = DCG@k / IDCG@k（IDCG 为 0 时该 topic 不参与此项均值）
```

这里的 `gain(0/1/2)` 需先由标注指南决定，不能照抄 `2^rel-1` 或其他库的默认权重。若任务只需要“找到一篇能回答的”，MRR/Hit@k 比 nDCG 更直观，不要为了指标多而引入假精度。原论文实际还讨论了不同 gain 和 log base 对结论的影响，所以实现与 trec_eval/其他库对数时必须固定公式，而不能只写“nDCG”。

**当前多路 top-10 特有两条限制**：

1. “每路前 10”和“去重归并后前 10”是不同 cutoff。主口径以调用方实际看到的清单为准，另附 `route/rank` 诊断定位是某路没召回还是归并后排序导致靠后；不要把每路名次平均后宣称是用户名次。
2. 失败路、默认隐藏 `other`、`keywordsDropped` 都不是零结果证明。主分数可把找不到 gold 记 0 以保持对失败的惩罚，但必须另报 `routeComplete = 成功路数/计划路数`、隐藏数、截断数；任何主分数旁附完整性，不让“部分成功”伪装成“官方没有”。

**离线变化验收**：比较对象使用完全相同的 topic/queryPlan、冻结上游字节和 gold，输出逐 topic 的 win/loss/tie 与总差值。小型集不以 `p > 0.05` 自动判“无差异”，也不以 p 值代替用户可见效果；NIST 的 CI 研究专门指出统计显著不意味着差异大或用户可感知 [S8]。以 bootstrap 对 topic（不是对文档）有放回重采样估计**均值/配对差值区间**是一种可复现的不确定性表达 [S8][S9]，但不能用 bootstrap 给本来不存在的 gold 或样本代表性“制造证据”。固定随机种子和 1,000–5,000 次重采样只是实现参数，不把小样本变成大样本。

## 4. 固定选词、自动选词与候选选择的归因

### 4.1 控制变量，而不是拿两套全流程结果互猜

| 实验单元 | 给内核的输入 | 选择全文方式 | 归因 |
|---|---|---|---|
| A：参考查询 | 人工冻结 `keywords[]`、顺序、过滤 | 固定 rule 或人工 oracle | 内核 + 上游检索/归并 |
| B：宿主自动查询 | 同一 topic，隐藏参考 queryPlan，冻结宿主/提示/模型版本 | 与 A 相同 | B−A 主要是自动选词及其顺序差异 |
| C：自动候选选择 | 与 A/B 各自相同候选清单 | 宿主按既有规则选择，最多 K 帖 | 在相同清单上测选择，不混到 search recall |
| D：固定证据读取 | 指定 doc id 与所需 evidence | read | 全文归一化、分页/详情/截断/失败处理 |

B 必须保留真实宿主请求、模型与提示版本、生成 token、重试次数和最终实际 queryPlan。否则无法区分“选词差”与“宿主根本没有按约定调用”。A/B 使用同一冻结 run 时得到**条件于该上游快照**的差分；不把跨周自动查询与昨天人工查询的差分全归给选词。若要在线比较，在获准协议下配对/交错小批测量并保留时间，且仍以上游漂移为混杂因素。

### 4.2 候选选择与全文证据分开判分

- **selection@K**：在相同候选清单上，选中帖与金标 relevant/essential 集合的命中情况。记录 `selected_ids`、候选版本、K、放弃项和理由；同时报 selected precision、knownGoldRecall、无关首选率。只测“前 K 清单含相关”不能证明宿主会读到它。
- **read evidence**：固定 doc 后，所需证据要点是否出现在返回正文/最佳回答/其他回答/追问中，是否能用 `(type,id,answer_id,section 或文本锚点)` 回到原文。逐要点 `covered/partial/missing`；不得因字段非空就称证据完整。
- **证据正确性**：人工按当前产品/版本验证关键机制、字段名、步骤与限制。`adopted` 仅是社区信号，不能替代该判断；错误但被采纳的回答必须能被判不合格。
- **read 完整性**：`answersTaken/answersTotal`、`truncated`、route errors、缺页/失败详情、是否只有摘要而非全文分别报告。当前 `truncated=answer_limit` 与 `upstream_error` 可区分“达到详情上限”和“上游故障”，但无法单独表达所有页级失败规模，不能进一步虚构已读全。
- **端到端任务**：用自动选文后 read 的证据对预设任务 rubric 判定“证据充分/部分/不足”，不评价最终自然语言答案，避免把生成能力混进来。该分由 `检索 × 选文 × 读取 × 原文正确性` 共同决定，不能回写成 search 分数。

## 5. 可复现的在线采样、快照与离线重放

### 5.1 三层数据不能混名

| 层 | 保存什么 | 能证明 | 不能证明 |
|---|---|---|---|
| 行为 fake | 人工构造边界、错误、并发时序 | 逻辑分支、契约与退化行为 | 在线内容质量、真实网络延迟 |
| 真实响应快照 | 经许可取得的请求上下文、响应头/体、时间、哈希 | 归并、解析、同一候选上的比较、当时证据 | 今日上游全集、实时延迟、未来 SLA |
| 在线测量 | 单调时钟事件、全部尝试与结果 | 当时/环境/客户端下的体验分布 | 永久排名、无样本区间的尾部、上游承载上限 |

快照不是把 HTML/JSON 一起塞入现有 fake 就结束：每条应含 `request_id, topic_id, layer, kernel/contract commit, host/prompt/model, queryPlan, normalized URL, request headers 的必要子集, status, response headers 白名单, body bytes/encoding, sha256, started/finished UTC, attempt, cache_state`。金标另存，不从被测输出自动派生。保留原始响应用于重放归一化；保存公开输入输出用于契约回归；所有个人问题、日志 URL 参数和正文在入库前做隐私/许可复核。

用 `time.monotonic_ns()` 测量耗时，UTC wall-clock 只作时间戳；一次调用从进入到结果可消费为止（time-to-last-byte/投影完成），不只测 socket 连接或首个响应。每次尝试都记录 `route/kind/page/answer_id`、排队/网络/解析阶段、状态与错误分类，确保 `upstreamCalls` 可和真实尝试对账。重试、重定向、缓存验证都是新的尝试/事件，不能隐藏到“单次请求”分母之外。

### 5.2 离线回放能替代什么

冻结字节和可注入 clock 可以重放：排序/去重、证据归一化、gold 评分、超时/重试策略的状态机、注入延迟下的 deadline、字节与 token 计数。用 fake 模拟慢响应、429 + Retry-After、503、ETag/304 及缓存过期，**这些是协议测试，不是上游发生过这些状态的证据**。

它不能重放真实 RTT、DNS/TLS、代理/CDN、拥塞、上游查询计算、跨进程竞争和排名漂移。录下的 elapsed 只能作为历史观测，不能在离线回放后当作当前 P95。只有经许可的、定义明确的在线测量才能支持在线延迟声明；比较前先校验快照 schema/body hash、gold 版本和实现版本，不能用新解析器“修正”历史响应后再把差异算作质量提升。

## 6. 延迟、请求/字节/token 与缓存：如何计账

### 6.1 延迟与尾部的正确表达

Google SRE 原始书章强调延迟应看分布，mean 会掩盖长尾，高阶 percentile 表征较差尾部，中位数表征典型情况；还应写明测量窗口、请求范围、采集点和 time-to-last-byte 等口径 [S10]。NIST 指出不同 quantile 插值方法在小样本下结果不同 [S9]，因此固定一种 quantile 定义、保留全部原始观测，并同时报 `N/max/failure_count/censored_count`。

建议按 `operation × route_count/kind × cache_state × cohort` 分开报 P50/P95/max，不把 search 路由、question 页、read 全文混为“每次 HTTP 延迟”，也不把热缓存和冷启动混为一个总体。

- **试运行**：约 20 个独立操作只能展示这批观测的分位数和最大值，P95 接近尾部单个次序统计量，不足以宣称长期 P95 达标。
- **正式比较（建议门槛而非标准定律）**：每 cohort 争取至少 100 个**跨时间、相互尽量独立、同一操作类别**的操作，且与另一版本同时间片交错，累计数周而非瞬间打完；P95 才比 max 多一点实际观测支撑。仍须报告区间、离群点与失败，不能凭 100 推断 P99。
- **预算优先**：若许可的请求预算不足以支撑 P95，就把结论降为“P50、观测最大值与尾部个案”，不要为得到漂亮 P95 重复轰炸上游。零失败不能证明高可用，20 秒超时也截断了可观测尾部。
- 超时、取消、失败和部分结果**不可从延迟样本中删除**。除成功分布外报告其比例及总 deadline；`ok:true` 但 routeErrors/证据截断的操作归 degraded，不与完整成功同组。时间上限处是右删失/未知后续，不是证明服务会在该时延返回。

SLI/SLO 是本地用户体验指标/目标，SLA 是包含未达后果的协议 [S10]。本仓可定义自己的客户端验收目标，**不能反向宣称金蝶承诺该目标**。目标先由个人任务可接受等待时间和首次小规模基线决定，不在本研究凭空规定“P95 必须 X ms”。

### 6.2 每次任务必须可核对的账

```text
attempts = 初次请求 + 重试 + 重定向 + 缓存条件验证
upstream_bytes = 实际响应头/体（声明是否含头、是否压缩前后）
evidence_chars/tokens = 投影后交给宿主的正文/引用定位，而非仅原始响应
host_tokens = 自动选词与候选选择的输入/输出，单独于内核记账
deadline_ms = 宿主可感知总预算，涵盖排队、网络、重试、解析
concurrency = 本机三端合计在飞上限，不是各进程各自的 burst
```

请求预算是**验收前先要设定的自限参数**，依据许可、任务价值和实测成本决定，不是标准给出的每秒数字。每 topic 给 search/read 分别的上限，另给整个工作流总上限和熔断；预算耗尽返回明确 `partial/budget_exhausted`，不能以隐式停止改善延迟。当前 question 的页数未知，因此规格若要求有界成本，必须新增明确的页/详情/字节上限及可续取游标或部分结果，而不是在测评脚本外面截断后宣称内核有界。

三端至少在一个用户级场景中验证聚合预算与计数隔离：同一进程并发的 A/B 调用不串 `upstreamCalls/elapsedMs`；三个进程/宿主的速率、缓存与取消作用域被明确记录。可用本机假 HTTP 服务测超时、慢 body、重试、并发和预算，不触金蝶；真实网络只验证已获准的小样本。

### 6.3 缓存命中率不能单独证明优化

RFC 9111 定义 fresh response 可在不联系源站时复用；cache key 至少包含 method + URI，Vary 指定的请求头也必须匹配 [S11]。应用层缓存还应加入本仓有语义的 `product/global/sorts/page/pageSize/type/id/include_other/版本/归一化策略`，不能只按标题或关键词字符串复用。

至少分四类：

| 结果 | 上游尝试 | 解释 |
|---|---:|---|
| fresh hit | 0 | 真正减少上游调用；需证明命中语义相同 |
| stale + validation 304 | 1 | 通常省 body 不省请求，不能计入零上游命中 |
| stale + validation 200 | 1 | 更新副本；不能称省了一次请求 |
| miss | 1 | 实际请求；失败缓存另列，不默认缓存错误/空结果 |

报告 `lookup_count` 为分母、上述分子、`byte_saved_estimate`、新鲜度/age、失效率、证据 drift 和错误复用数。暖缓存快并不自动好：陈旧的搜索排序或回答会损害证据新鲜度。RFC 允许在特定条件下启发式新鲜度，提到 Last-Modified 间隔的一个常见比例为 10%，但它不是本仓可套用的 TTL，且显式过期时禁止另用启发式 [S11]。search 与 question read 是否需要不同 TTL/重新验证由实测漂移决定；未证实上游 validators 前不承诺 ETag 优化。HTTP `no-cache` 是必须重新验证，不等于 `no-store` 禁止存储 [S11]。

## 7. 标准 HTTP 重试、超时、缓存语义及本仓采用边界

### 7.1 重试不是“全部错误重试三次”

- GET 是 safe/idempotent 的方法，通信失败使客户端读不到响应时，自动重试其**预期效果**仍相同；服务器仍可记录每次请求 [S12]。这意味着可以设计有界重试，不意味着没有上游成本，更不推翻 robots/许可要求。
- 429 表示某窗口内请求过多，响应**可以**带 Retry-After；服务端并不被要求一定使用 429，识别用户及计数窗口也由服务端决定 [S13]。不能把一次没有 429/限流头外推成“无速率限制”。
- `Retry-After` 可为 HTTP-date 或收到响应后延迟的非负整数秒；503 时表示预期不可用多久，3xx 时表示跟随重定向前的最低等待 [S12]。在 429 上它由 RFC 6585 允许，语义应与限速等待一致处理。解析后服从总 deadline 与许可的最大等待；无效/过去日期不能变成忙循环，超出本地 deadline 则明确失败而不是无限睡眠。
- 将 408（服务端请求超时）、429、500、502、503、504 与可判定的连接重置/socket timeout 作为**候选可重试类**；400/401/403/404/422 与 schema/输入错误不默认重试。连接前失败、已发送后响应丢失、body 半途失败分别记类；所有类仍受 attempts、deadline、预算和幂等性限制。上游 HTTP 200 + `errorCode` 必须按其业务语义分类，不可因为传输成功而一律重试。
- 有 Retry-After 先按它等待（受上限约束）；否则使用有上限指数退避加 full jitter：`sleep = U(0, min(cap, base * 2**retry_index))`。AWS 官方 SDK 文档解释 full jitter 可打散同时重试形成的洪峰，并把 retry 次数、错误分类和 quota 结合 [S14]；其中 50ms/1s/20s/3 次是 AWS 服务的具体选择，**不是 HTTP 标准，也不是本仓应照抄的阈值**。
- 本仓可先用 fake 验证“最多 2 次总尝试”作为保守起点，但是否需要第二次尝试、base/cap 和等待上限须由许可与体验目标决定。不要把建议起点写成测量结论。发生 429/连续 5xx 时默认熔断并退避，不做重试直到成功，不做跨端重试风暴。
- 当前 20s 是 `urlopen` 的阻塞操作超时；Python 文档说明它作用于连接等 blocking operations，不是完整工作流 deadline [S15]。需用本地假服务测 connect/read/total/cancel 的关系，不能用单请求 20s × 未知页数推导最大交互时延。

### 7.2 条件请求与缓存不是零请求

已有验证器时，RFC 9111 要求用 ETag 的 `If-None-Match`，适用时用 Last-Modified 的 `If-Modified-Since`；没有 ETag 时才能主要依赖后者 [S11]。304 更新本地元数据后复用表示，**仍发生网络验证**。Vary、no-store/no-cache、fresh/stale 与 disconnected stale 的条件按 RFC 处理 [S11]，不能自造“永久缓存 + 后台随意刷新”。

本仓尚未核实各 API 响应的 Cache-Control/ETag/Last-Modified/Vary/Age，也未证明它们对匿名动态搜索稳定有效；需在许可下观察，不可从网页主页头推断 API。没有验证器时可选择明确、可撤销的短期应用缓存，并显示 age，但它不是 HTTP revalidation 的替代物，也不自动让缓存命中成为正确证据。

## 8. 上游礼貌：已核实事实、未知与低频候选协议

### 8.1 已知与未知

**已核实**：

- 上游 robots 文件存在，通配组为 `Disallow: /`，具名例外并不包括当前内核。RFC 9309 的匹配与访问规则见 [S1]。
- 当前项目自动请求接口、生成查询与展开回答页，具有程序化自动访问属性；人工在浏览器阅读一篇公开帖子不是同一件事。浏览器 UA 字符串、匿名访问和 GET 方法都不能证明爬虫许可。
- 当前本地 burst/rps 仅是项目自限配置，不是上游 SLA。RFC 6585 明确服务端可以不发送 429 [S13]。

**未验证，不能写成事实**：

- 金蝶是否针对这些私有/网页 API 提供独立使用许可、robots 是否意图覆盖 API、具体允许的身份/UA/频率、缓存保存期限和再分发权限。
- 是否存在面向匿名社区 search/read 的 SLA、延迟/可用性承诺、分钟/小时级限速、CDN 缓存规则。公开检索没有定位到可核验的此类承诺，不能将“未找到”写成“不存在”。
- `/agreement` 的直接抓取返回了社区外壳/404 内容而非可用协议正文，因此没有取得可以支持 API 许可的条款。也不能由该结果断言社区没有协议。
- 429、Retry-After、RateLimit、ETag 等在本轮 search/read 上是否出现；本轮没有为此调用 API。

### 8.2 启动在线验收的前置闸门

1. 维护者向上游确认程序化 search/read 是否被许可，其 UA、用途、频率、数据保存和展示限制；保留答复/适用条款。若 robots 适用且无例外，**停止自动在线检索路线或改用获授权 API/人工导出资料**，而不是伪造 Googlebot UA、换 IP、加 cookie 或提高并发规避。
2. 若没有书面 SLA，就只定义本机 SLI/自限预算，不对外承诺上游稳定性。任何“建议低频率”都不是许可替代品。
3. 取得许可后先在本地假服务验证 deadline、重试、预算、跨端聚合计数与日志隐私；再以最小 search/read smoke 检查 schema/headers，不扩成排名/并发压力测试。
4. 把自动采样放在固定、低频的人工触发评审中；默认串行、小批、间隔执行，失败即停，禁止 nightly cron 全量重放、全库扫描、并发爬升、重试风暴。若上游给更严约束，以更严者为准。
5. 每次复用 robots 缓存不超过 24h（RFC 9309 的建议）并重新确认适用规则；遇到 4xx/5xx/网络不可达按其不同语义处理 [S1]。任何 403/429/明确拒绝都停止对应实验，而非通过变换词继续打。

### 8.3 经许可后的最小观察计划（未执行）

- **建立内容金标**：一次性、分层抽取小批 topic 的 search 响应与所需全文，足够构建多来源候选池；只读取人工准备评价的少量候选，不为“top-N 更多”自动翻遍结果页。快照后离线做主要比较。
- **建立延迟基线**：选择典型 `1–3` 路 search、`knowledge/article/question` 各少量 read，及经许可的最大路数/长问答边界；同一小批 topic 交错观察版本，逐步累计跨天/周的样本。预设总尝试和字节上限，超出就只报告观测值，不补样本凑 P95。
- **低频复验**：由维护者手动在发布候选或月度评审时运行固定小子集；每个 cohort 给明确请求/字节/日期/截止时间上限。这里的“月度”是本仓可选自限节奏，不是安全许可或统计充分保证；若无需新证据就不联网。
- **复验对象**：连通/schema、证据 drift、失败/截断、延迟与预算，不能只有 200 OK。若要量化在线排名变动，重复同 query 时保留时间与响应哈希，区分上游 drift 与代码变化；不能把热缓存响应作为新样本。

## 9. 建议的最小验收矩阵

| 变化 | 必须具备的证据 | 仍需披露 |
|---|---|---|
| 修改归并/首页深度/排序 | 同一冻结 run/qrels 的 Hit/knownGoldRecall/MRR，必要时 nDCG；逐 topic win/loss/tie、失败/隐藏/截断 | gold 覆盖、未标注候选、上游快照日期、跨快照稳定性 |
| 修改宿主选词/提示/模型 | 固定参考计划 A 与隐藏参考的自动 B，同 run 配对；宿主 token/调用次数；留出集 | 上游时间漂移、模型版本、人工查询成本、是否能跨宿主复现 |
| 修改候选选择/深读策略 | 相同候选上的 selection@K 与无关首选率；全文 evidence coverage 与错误/截断 | 原文本身是否可回答、宿主选择成本、读取 K 的请求/字节 |
| 修改 read 分页/展开 | 固定 doc 的要点覆盖、定位、完整性/失败页；尝试数、字节、deadline | 当前 `P` 无界，任何新上限造成的截断必须可续取/可见 |
| 引入缓存 | 四类命中/验证、age/drift/错误复用、相同 gold 质量不变；冷/暖延迟分开 | 节省的是请求还是仅字节，跨端共享/隐私、无 ETag 时新鲜度依据 |
| 引入重试/并发/连接复用 | 本地假 HTTP 的状态/时序/取消/幂等/预算测试；获准在线的小样本 P50/P95/max/失败 | 重试后的总尝试、总延迟与上游成本；进程内限速不是三端上限 |
| 性能验收 | 明确 operation/cohort、N、clock、time-to-last-byte、原始观测、P50/P95/max/失败/删失 | 小样本尾部不足、网络环境、缓存状态、非上游 SLA |

**建议的证据门槛顺序**：先有可审查的 querySet/qrels/证据片段与上游许可 → 固定输入离线可复现 → 本地协议/预算故障注入通过 → 获准在线最小基线 → 才决定性能/缓存/排序优化。若第一层未满足，禁止用 47 个回归或一个 P95 数字宣告检索质量通过。

## 10. 未验证项与建议下一步

### 10.1 本研究没有证明

- 没有取得或构建新的金蝶领域查询集/qrels，没有测当前检索的 Hit/Recall/MRR/nDCG 或选择/全文任务成功率。
- 没有在线测量 P50/P95、漂移、错误率、缓存头、长窗口限流，也没有验证三端聚合速率/缓存命中；没有执行任何压力、并发上限或深度分页测试。
- 没有证明快照协议在不同上游 schema 漂移下完整可重放，没有测量正文 token/tokenizer（内核不生成答案，也没有天然统一 tokenizer）。
- 没有取得上游 API 许可、SLA 或 robots 对 API 意图的解释；当前 robots 发现使自动在线验收**条件性阻塞**，不是单纯“少测一点”。
- 没有为某个延迟/预算/recall 数字设定已验证的合格线；上述样本量、重试起点和月度节奏是待批准的测量纪律，不是实测推荐上限。

### 10.2 给地图/规格的实施顺序

1. **先解决上游规则适用与许可**（阻塞在线路线），记录正式答复；不要通过 UA 伪装或提高请求频率规避。
2. 以真实任务建立小型、版本化 querySet/queryPlan/qrels/evidence；先完成标注指南与双标抽查，再谈任何阈值。
3. 设计**独立测量/记录边界**（可在后续规格中决定放内核还是测试工具）：统一 attempt_id、route/page/answer 维度、monotonic clock、原始字节与上游错误；将缓存 hit/revalidated/miss 和失败/degraded 纳入账目。
4. 复用现有 fake 做协议测试，另建许可快照做 gold replay；两者分别命名，禁止用离线 elapsed 支持在线 SLA。
5. 先给当前实现建立基线，再一次只改一层（选词、归并、选择、read、缓存），用第 9 节矩阵比较；不要先引入本地向量库、共享常驻服务或复杂排序器再找指标。
6. 明确 question read 的成本上限/续取模型与三端共享预算归属，然后才能对总延迟/请求给出可信验收；若不要求有界 read，规格必须明确其由上游页数决定的事实。

- **[S1] Robots**：[RFC 9309 §2.2.1–2.2.2](https://www.rfc-editor.org/rfc/rfc9309.html#name-the-user-agent-line)、[§2.3](https://www.rfc-editor.org/rfc/rfc9309.html#name-access-method)、[§2.4](https://www.rfc-editor.org/rfc/rfc9309.html#name-caching)；[`vip.kingdee.com/robots.txt`](https://vip.kingdee.com/robots.txt) 原文快照（取得时内容如文首的“结论先行”）；每次 robots 查询也已计入本轮上游访问记录。
- **[S2] 查询/金标/pooling**：[NIST, How To TREC — TREC Lingo 与数据集说明](https://trec.nist.gov/howto.html)。
- **[S3] 标注差异**：[Ellen M. Voorhees, *Variations in Relevance Judgments and the Measurement of Retrieval Effectiveness*, NIST 出版页](https://www.nist.gov/publications/variations-relevance-judgments-and-measurement-retrieval-effectiveness)（结论限于其 TREC 集合与相对比较，不外推为单条标注正确）。
- **[S4] 偏好判断**：[Carterette et al., *Here or There: Preference Judgments for Relevance*, ECIR 2008, Microsoft Research 出版页及原文链接](https://www.microsoft.com/en-us/research/publication/here-or-there-preference-judgments-for-relevance/)，原文 §3–4、§6。
- **[S5] 不完整判断**：[Buckley & Voorhees, *Retrieval Evaluation with Incomplete Information*, SIGIR 2004, NIST 原文 PDF](https://tsapps.nist.gov/publication/get_pdf.cfm?pub_id=150469)，§1–2、§6。
- **[S6] Reciprocal rank**：[NIST TREC 论文示例，§3.6 Mean Reciprocal Rank](https://trec.nist.gov/pubs/trec34/papers/DUTH.tot.pdf)。该处用于核对定义，不把其另一任务的分数迁移到本仓。
- **[S7] nDCG**：[Järvelin & Kekäläinen, *Cumulated Gain-based Evaluation of IR Techniques*, TOIS 20(4), 2002, 作者机构出版信息](https://researchportal.tuni.fi/en/publications/cumulated-gain-based-evaluation-of-ir-techniques/)；[原文公开 PDF](https://www.fi.muni.cz/~xkohout7/Research/clanky_cizi/evaluation/p422-jarvelin.pdf)，§1–2、§4。
- **[S8] 小样本差异与 CI**：[Ian Soboroff, *Computing Confidence Intervals for Common IR Measures*, NIST 原文 PDF](https://tsapps.nist.gov/publication/get_pdf.cfm?pub_id=917303)，§1–4。其 CI 对象是 topic 指标均值/重复实验，不是延迟 P95 的通用充分样本量证明。
- **[S9] 分位数与 bootstrap**：[NIST/SEMATECH Handbook, Percentiles](https://www.itl.nist.gov/div898/handbook/prc/section2/prc262.htm)、[Bootstrap Plot](https://www.itl.nist.gov/div898/handbook/eda/section3/bootplot.htm)。
- **[S10] 延迟/SLI/SLO/SLA**：[Google SRE Book, *Service Level Objectives*, Indicators / Aggregation / Agreements](https://sre.google/sre-book/service-level-objectives/)；[SRE Workbook, *Implementing SLOs*](https://sre.google/workbook/implementing-slos/)（将 degraded 单独计量的原则）。
- **[S11] HTTP 缓存**：[RFC 9111 §2–3](https://www.rfc-editor.org/rfc/rfc9111.html#name-overview-of-cache-operation)、[§4.1–4.3](https://www.rfc-editor.org/rfc/rfc9111.html#name-calculating-cache-keys-with)、[§5.2](https://www.rfc-editor.org/rfc/rfc9111.html#name-cache-control)、[§6](https://www.rfc-editor.org/rfc/rfc9111.html#name-relationship-to-applications)。
- **[S12] HTTP 方法/Retry-After**：[RFC 9110 §9.2.1–9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#name-safe-methods)、[§10.2.3 Retry-After](https://www.rfc-editor.org/rfc/rfc9110.html#name-retry-after)。
- **[S13] 429**：[RFC 6585 §4 与 §7.2](https://www.rfc-editor.org/rfc/rfc6585.html#section-4)。
- **[S14] 有界指数退避/full jitter 实例**：[AWS SDKs and Tools, Retry behavior](https://docs.aws.amazon.com/sdkref/latest/guide/feature-retry-behavior.html)（官方实现的参考，不是金蝶或 HTTP 的默认参数；文档注明的版本开关也不能忽略）。
- **[S15] Python timeout**：[Python `urllib.request.urlopen` 文档](https://docs.python.org/3/library/urllib.request.html#urllib.request.urlopen)。
- **[L1] 本地行为基线**：[场景计数、elapsed/限速/请求口径](../../tests/baseline/public-behavior-baseline.json#L1-L11)、[重放器关于固定 fake 的说明](../../tests/baseline/replay_baseline.py#L16-L23)。
